# Data Pipeline — Single Source of Truth

## The Problem This Rule Solves

Numbers were living in three places at once (projection JSON, target-portfolio.json, sub-strategy .md files) with no automatic propagation. Every manual edit created drift. Agents would read whichever file they found first and give contradictory answers.

## The Law

> **Code drives data. Data drives documents. Documents never hold canonical numbers.**

Every number in a `.md` file (price, fair value, entry gate, weight) is a **rendered view** of a JSON source. If the JSON changes, the `.md` must be regenerated by code. If you find yourself editing a number directly in a `.md` file, stop — update the JSON source and run the propagation script.

---

## Source of Truth Hierarchy

```
projections/{TICKER}.json          ← canonical DCF output per stock
        ↓  (on every DCF run)
target-portfolio.json holdings[]   ← standing decisions, entry gates, weights
        ↓  (on every thesis change)
theses/sub_strategies/*.md         ← rendered view only — never edit numbers directly
        ↓
Dashboard / UI                     ← reads from target-portfolio.json
```

**One direction only. Never backwards.**

---

## Non-Negotiables

1. **DCF run → propagate immediately.**
   After any `/evaluate-stock` or DCF script run, call `propagate_dcf.py {TICKER}` before ending the session. Never leave `projections/{TICKER}.json` updated while `target-portfolio.json` still holds stale numbers.

2. **Trade executes → update both portfolio and thesis.**
   After any buy or sell: update `portfolio.json` (shares, book_price) AND update `target-portfolio.json` (role, targetWeight, standingDecision). Both in the same turn. No exceptions.

3. **Standing decision is the single trade signal.**
   The `standingDecision` field in `target-portfolio.json` is the only field an agent reads to decide BUY / WAIT / DO NOT CHASE. It must always reflect the most recent DCF output and user confirmation. Raw DCF output from `projections/*.json` is an input to the standing decision — never a replacement for it.

4. **Sub-strategy .md files are read-only for numbers.**
   Never hardcode prices, fair values, entry gates, or weights in `.md` files manually. All numeric tables in sub-strategy docs are regenerated by `update_thesis.py`. If a number in a `.md` file is wrong, the fix is in the JSON — not in the `.md`.

5. **`target-portfolio.json` uses `ticker` key, not `symbol`.**
   All code that reads holdings must use `h.get('ticker')`. Using `h.get('symbol')` silently returns None for every holding.

6. **Before any recommendation, read live price vs standing decision.**
   Never surface a DCF action (BUY/SELL/HOLD) from `projections/*.json` without first reading the `standingDecision` in `target-portfolio.json`. The standing decision includes user-confirmed entry gates that override raw DCF signals. Always compare the live price to `standingDecision` entry gates before giving a trade recommendation.

---

## Propagation Script: `propagate_dcf.py`

**Required behavior** (implement in `plugins/portfolio-advisor/scripts/propagate_dcf.py`):

```
Input:  TICKER, projections/{TICKER}.json
Output: target-portfolio.json holding updated with:
          - agentRationale (fresh DCF summary)
          - priceLevels.buyTiers (from DCF FV with MoS)
          - priceLevels.sellTiers (from DCF FV)
          - standingDecision.reEntryNote (updated FV)
        theses/sub_strategies/{relevant}.md regenerated:
          - Valuation Gate Results table updated
          - Entry Rules section updated
          - Analyzed date updated
```

Until `propagate_dcf.py` exists, after every DCF run manually:
1. Update `target-portfolio.json` standing decision entry gate to match new FV
2. Flag any `.md` file that shows a stale price/FV with `⚠ STALE — run propagate_dcf.py`

## Conflict Resolution

When numbers conflict across files, priority order:

| Priority | Source | When authoritative |
|----------|--------|--------------------|
| 1 | `target-portfolio.json` `standingDecision` | Always — user-confirmed |
| 2 | `projections/{TICKER}.json` `aiThesis.fairValue` | After a fresh DCF run |
| 3 | `theses/sub_strategies/*.md` tables | Never — rendered view only |

If Priority 2 conflicts with Priority 1 by **>15%** in fair value → flag conflict explicitly to user and ask whether to update the standing decision. If **≤15%** → it is noise, do not change the standing decision.

---

## What "Stale" Means

A projection is stale if `projections/{TICKER}.json` `aiThesis.analyzedAt` is older than 30 days.
A standing decision is stale if `target-portfolio.json` `standingDecision.source` date is older than the projection date.

Both must be refreshed before initiating or sizing a position.
