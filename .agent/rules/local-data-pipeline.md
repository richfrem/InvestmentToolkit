# Data Pipeline — Single Source of Truth

## The Problem This Rule Solves

Numbers used to live in three places at once (projection JSON, a thesis JSON file, sub-strategy .md files) with no automatic propagation. All portfolio and thesis data is now in `domain_model.sqlite` (ADR-038); the files that used to hold it are retired. Every manual edit created drift. Agents would read whichever file they found first and give contradictory answers.

## The Law

> **Code drives data. Data drives documents. Documents never hold canonical numbers.**

Every number in a `.md` file (price, fair value, entry gate, weight) is a **rendered view** of the database. If the database changes, the `.md` must be regenerated by code. If you find yourself editing a number directly in a `.md` file, stop — update the database through its script and regenerate.

---

## Source of Truth Hierarchy

```
projection_version / projection_scenario (domain_model.sqlite)  ← canonical DCF output per stock
        ↓  (on every DCF run: update_price_levels.py, update_targets.py)
investment.* + price_level_tier (domain_model.sqlite)            ← standing decisions, entry gates, weights
        ↓  (on every thesis change: generate_portfolio_blueprint.py)
theses/sub_strategies/*.md         ← rendered view only — never edit numbers directly
        ↓
Dashboard / UI                     ← reads from domain_model.sqlite
```

**One direction only. Never backwards.**

---

## Non-Negotiables

1. **DCF run → propagate immediately.**
   After any `/update-stock-analysis` or DCF script run, call `propagate_dcf.py {TICKER}` before ending the session. Never leave a projection updated while the stored price levels and standing decision still hold stale numbers.

2. **Trade executes → update both portfolio and thesis.**
   After any buy or sell: sync the broker positions (`/tv-portfolio-sync`, shares and book price land in `account_investment`) AND update the thesis fields (`lifecycle_status`, `target_weight`, standing decision) with `update_targets.py` / `update_thesis.py` / `set_standing_decision.py`. Both in the same turn. No exceptions.

3. **Standing decision is the single trade signal.**
   `investment.standing_decision_type` / `standing_decision_reason` (domain_model.sqlite) is the only field an agent reads to decide BUY / WAIT / DO NOT CHASE. It must always reflect the most recent DCF output and user confirmation. Raw DCF output from `projection_version` is an input to the standing decision — never a replacement for it.

4. **Sub-strategy .md files are read-only for numbers.**
   Never hardcode prices, fair values, entry gates, or weights in `.md` files manually. All numeric tables in sub-strategy docs are regenerated by `update_thesis.py`. If a number in a `.md` file is wrong, the fix is in the database — not in the `.md`.

5. **Holdings use `ticker` in API/JSON payloads and `symbol` in SQL.**
   `portfolio_io.load_thesis_holdings()` returns dicts keyed `ticker`; `investment` rows have a `symbol` column. Using the wrong key silently returns None for every holding.

6. **Before any recommendation, read live price vs standing decision.**
   Never surface a DCF action (BUY/SELL/HOLD) from a projection without first reading the standing decision on the `investment` row. The standing decision includes user-confirmed entry gates that override raw DCF signals. Always compare the live price to `standingDecision` entry gates before giving a trade recommendation.

## Propagation Script: `propagate_dcf.py`

**Required behavior** (implement in `plugins/portfolio-advisor/scripts/propagate_dcf.py`):

```
Input:  TICKER, its latest projection_version
Output: the investment row and its price levels updated with:
          - agent_rationale (fresh DCF summary)
          - price_level_tier buy tiers (from DCF FV with MoS)
          - price_level_tier sell tiers (from DCF FV)
          - standing decision re-entry note (updated FV)
        theses/sub_strategies/{relevant}.md regenerated:
          - Valuation Gate Results table updated
          - Entry Rules section updated
          - Analyzed date updated
```

Until `propagate_dcf.py` exists, after every DCF run manually:
1. Update the standing decision entry gate in `domain_model.sqlite` to match the new FV (`set_standing_decision.py`)
2. Flag any `.md` file that shows a stale price/FV with `⚠ STALE — run propagate_dcf.py`

## Conflict Resolution

When numbers conflict across files, priority order:

| Priority | Source | When authoritative |
|----------|--------|--------------------|
| 1 | `investment.standing_decision_*` | Always — user-confirmed |
| 2 | latest `projection_version.fair_value` | After a fresh DCF run |
| 3 | `theses/sub_strategies/*.md` tables | Never — rendered view only |

If Priority 2 conflicts with Priority 1 by **>15%** in fair value → flag conflict explicitly to user and ask whether to update the standing decision. If **≤15%** → it is noise, do not change the standing decision.

---

## What "Stale" Means

A projection is stale if its `analyzed_at` is older than 30 days.
A standing decision is stale if `standing_decision_source` is dated before the latest projection.

Both must be refreshed before initiating or sizing a position.
